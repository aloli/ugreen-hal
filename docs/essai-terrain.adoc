= Fiche d'essai sur matériel — DXP2800
:toc:
:sectnums:

Fiche à dérouler devant le NAS, et à remplir au fur et à mesure. Chaque section indique ce qu'on cherche à établir, la commande, et ce qu'il faut noter — y compris en cas d'échec, car un échec précisément décrit vaut mieux qu'un succès vague.

== Reprise de séance (après la soirée du 29/07/2026)

[IMPORTANT]
====
*SystemRescue est un environnement live, en RAM.* Tout ce qui a été installé ou configuré pendant la dernière séance (paquet `i2c-tools`, modules chargés, mot de passe root, règles `nftables` vidées) est perdu au moindre redémarrage du NAS. Seuls les réglages du *BIOS* (watchdog désactivé, Secure Boot désactivé) sont persistants — pas besoin d'y retourner.
====

=== Voie rapide : un seul script

Une fois SystemRescue démarré et le câble branché sur le Flint (le réseau s'obtient par DHCP sans configuration manuelle), tout ce qui suit peut se rejouer en une commande :

[source,shell]
----
curl -sL https://raw.githubusercontent.com/aloli/ugreen-hal/development/scripts/systemrescue-restore.sh | sh
----

Le script (`scripts/systemrescue-restore.sh`) charge les modules SMBus/i2c, vide le pare-feu par défaut, installe une clé SSH *dédiée* à ce banc (pas de mot de passe root — voir l'en-tête du script pour la raison, un script tuyauté ne peut pas répondre à un prompt interactif), installe `i2c-tools`, puis détecte automatiquement le bus SMBus et scanne l'adresse `0x3a`.

Connexion ensuite depuis le Mac, avec la clé dédiée :

[source,shell]
----
ssh -i scripts/nas-ssh/id_ed25519 root@<IP-du-NAS>
----

[NOTE]
====
Ce chemin suppose le fichier poussé sur `origin/development`. S'il n'est pas encore disponible en ligne, dérouler la séquence manuelle ci-dessous.
====

=== Voie manuelle (détail de ce que fait le script)

Acquis de la dernière séance, pour mémoire : réseau en service via le pont GL.iNet Flint (voir `docs/reseau-banc.adoc`), contrôleur SMBus confirmé `8086:54a3` sur le bus `i2c-11`, adresse `0x3a` confirmée par sonde directe.

[source,shell]
----
# 1. Démarrage : Ctrl-F12 -> UEFI: USB
#    (l'ordre de boot n'a pas été changé, à refaire à chaque fois)

# 2. Charger les modules SMBus/i2c (silencieux si succès)
modprobe i2c-i801 i2c-dev

# 3. Vérifier le réseau (le Flint doit être allumé et déjà configuré)
ip -br a
ping -c 2 9.9.9.9

# 4. Mot de passe root, obligatoire pour sshd
passwd

# 5. Si ssh échoue en « No route to host » malgré un ping qui passe :
#    nftables de l'image live rejette le port 22, sans rapport avec le
#    routage. Vidage sans risque dans cet environnement jetable.
nft flush ruleset

# 6. Installer i2c-tools (nécessite le réseau)
pacman -Sy i2c-tools

# 7. Reconfirmer le bus et l'adresse (devrait redonner exactement 0x3a)
lspci -nn | grep -i smbus        # attendu : 8086:54a3, bus PCI 00:1f.4
i2cdetect -y -r 11                 # attendu : 0x3a présent dans la grille

# 8. NOUVEAU — pas encore tenté : lecture de bloc réelle à l'adresse
#    0x81 (état de la LED power), pour valider le protocole (format et
#    somme de contrôle) sous Linux avant de l'exposer côté FreeBSD.
i2ctransfer -y 11 w1@0x3a 0x81 r11@0x3a
----

Pour l'étape 8, retranscrire les 11 octets renvoyés, même en cas d'erreur. Vérification attendue : la somme des octets 0 à 8 (modulo 65536) doit correspondre aux deux derniers octets (somme de contrôle, poids fort puis poids faible) — voir `docs/protocol-i2c-leds.adoc`, section « Lecture d'état ».

[NOTE]
====
*Rien de ce qui suit n'écrit sur le stockage interne.* Le NAS démarre sur une clé USB, l'eMMC reste intacte. Le clone de sauvegarde (`scripts/backup-nas.sh`) ne conditionne que la phase 4, et n'est pas un prérequis de cette fiche.
====

== Étape 1 — BIOS

*Ce qu'on établit* : la touche d'accès, et l'état du watchdog.

[cols="1,4"]
|===
|✓ |Point

|☐
|Touche d'accès au BIOS. Annoncée : *Ctrl-F12*, d'après des retours d'utilisateurs, jamais vérifiée sur cet exemplaire. Candidats de repli : Suppr, F2, F7, F11, Échap. +
*À noter* : la touche qui a réellement fonctionné.

|☐
|*Désactiver le watchdog.* `Advanced` → `WatchDog Settings` → `Watch Dog Control` → `[Disabled]`. Réglé à 3 minutes par défaut (confirmé le 28/07/2026), il redémarre la machine en pleine session sinon — et le symptôme ressemble à s'y méprendre à une instabilité matérielle.

|☐
|*Désactiver le Secure Boot.* `Security` → `Secure Boot`. SystemRescue démarre même s'il est actif, mais *zVault ne démarrera pas* : FreeBSD n'a pas de chargeur signé pour les clés Microsoft. Autant le désactiver dès maintenant pour ne pas buter dessus à l'étape zVault. +
*À noter* : son état avant modification.

|☐
|Ordre de démarrage : *inutile d'y toucher.* Une fois le watchdog désactivé, `Ctrl-F12` → `UEFI: USB` suffit à chaque session, et garde UGOS (`Boot Option #1 = debian`) comme défaut sûr.
|===

== Étape 2 — SystemRescue : relevés, sans risque

*Ce qu'on établit* : la topologie du stockage interne, en confirmation des relevés faits par photo.

[source,shell]
----
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,LABEL
----

Attendu d'après `hardware-notes.adoc` : `mmcblk0`, 29,2 Gio, partitions `p1` à `p8` plus `p128`, dont `p6` étiquetée `UGREEN-SERVICE` et `p7` `USER-DATA`.

[cols="1,4"]
|===
|✓ |Point

|☐
|Sortie de `lsblk` — *à retranscrire intégralement*, c'est la confirmation directe des relevés photographiques.

|☐
|`lspci -nn \| grep -i smbus` : identifiant PCI exact du contrôleur SMBus. C'est lui qui déterminera si `ichsmb(4)` peut s'y attacher sous FreeBSD.

|☐
|`sudo i2cdetect -l` puis `sudo i2cdetect -y <bus>` sur le bus SMBus : *le contrôleur LED doit apparaître à l'adresse `0x3a`* (notation Linux, 7 bits). C'est la vérification la plus utile de cette étape — elle confirme l'adresse indépendamment de FreeBSD.
|===

|===

== Étape 4 — Le moment de vérité

*Ce qu'on établit* : si le protocole SMBus rétro-documenté fonctionne réellement.

[source,shell]
----
kldload smb                 # indispensable : c'est smb(4) qui crée /dev/smbN
ls -l /dev/smb*             # le device node doit exister
./ugreen-led-ctl status power
----

[IMPORTANT]
====
*Ne pas conclure trop vite.* Quatre causes distinctes produisent le même symptôme apparent — « ça ne marche pas ». Le code d'erreur les sépare. Voir la grille complète dans `protocol-i2c-leds.adoc` ; en résumé :

[cols="1,3"]
!===
!Ce qui s'affiche !Ce que ça désigne

!`ENXIO` / « Device not configured »
!Personne n'acquitte à cette adresse. *L'adresse ou le bus*, pas le code. Essayer un autre `/dev/smbN` s'il en existe plusieurs.

!`EINVAL` / « Invalid argument »
!Le noyau a refusé la requête avant le bus. *Notre code* — le contrôleur est hors de cause.

!Aucune erreur, valeurs cohérentes
!*Le protocole fonctionne.* Passer aux commandes d'écriture.

!Aucune erreur, valeurs aberrantes
!La trame passe mais n'est pas comprise. *C'est l'octet de longueur du bloc SMBus* — basculer sur `iic(4)`/`I2CRDWR`.
!===
====

[cols="1,4"]
|===
|✓ |Point

|☐
|Sortie exacte de `ugreen-led-ctl status power`, erreur comprise. +
*À retranscrire mot pour mot* : c'est la donnée la plus précieuse de toute la séance.

|☐
|Si la lecture réussit : `./ugreen-led-ctl off power`, puis `on`. *Observer la façade.* La LED a-t-elle réagi ?

|☐
|Si elle réagit : `./ugreen-led-ctl color power 255 0 0`. La couleur change-t-elle réellement en rouge ?
|===
