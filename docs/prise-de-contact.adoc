Title: Hardware support for UGREEN NASync NAS devices — intent to contribute

Hi,

I'm working on hardware support for UGREEN NASync NAS devices (starting
with the DXP2800, Intel N100) with the goal of contributing it to zVault.

The aim is not to build a competing distribution, but to document and port
the UGREEN-specific components that a stock FreeBSD base doesn't know
about:

- the front panel / drive bay LED controller (SMBus, slave address 0x3a in
  Linux 7-bit notation, chip ID 0xc5b2 — protocol already reverse-
  documented from the Linux reference implementation
  miskcoo/ugreen_leds_controller);
- the front panel buttons (GPIO, exposed on Linux via a platform driver
  rather than I2C);
- hardware monitoring (ITE IT8613 — FreeBSD's superio(4) already
  recognises the device ID via D39969, and a full it8613hwm(4) driver
  exists in review as D39970/D39971, currently "Changes Planned").

Work in progress is documented here, hardware findings first:
https://github.com/aloli/ugreen-hal

The core is deliberately distribution-agnostic (plain FreeBSD smbus(4) /
gpio(4)), with thin per-distribution packaging layers on top, so the same
driver work can serve zVault and other FreeBSD NAS distributions without
duplicating the hard part.

Two questions before I go further:

1. Is any similar work on UGREEN NASync support already under way on the
   zVault side? I searched this tracker and found nothing, but I'd rather
   ask than duplicate effort.
2. What contribution shape would be most useful to the team — an add-on
   module to zvio-os / zvio-middleware, or something more directly
   integrated?

For context on where this stands: the protocol is documented but not yet
validated on real hardware under FreeBSD. That's the next step, and I'll
report results either way.

Thanks for keeping TrueNAS CORE alive — that continuity is exactly what
I was looking for.

Philippe

Title: UGREEN NASync hardware support — extension in development

Hi,

I'm developing FreeBSD support for the UGREEN NASync range (DXP series,
Intel x86_64) — front panel and drive bay LEDs over SMBus, buttons over
GPIO, and ITE IT8613 hardware monitoring. None of this is supported out
of the box on a stock FreeBSD base today.

The driver core is plain FreeBSD (smbus(4) / gpio(4)) and carries no
dependency on any particular distribution. I'd like to package it as a
XigmaNAS extension, following the structure used by existing community
extensions (etc/ + gui/ PHP pages + init script + version file).

Repository, with the hardware findings and the reverse-documented SMBus
protocol:
https://github.com/aloli/ugreen-hal

Questions:

1. Is there any existing work on UGREEN hardware within the XigmaNAS
   community that I've missed?
2. For an extension of this kind, is a separate repository referenced from
   the project the expected route, or would you rather see it proposed
   into the main tree?

Philippe

== `miskcoo/ugreen_leds_controller` — commentaire pour l'issue #111

Contexte : lors de la première validation matérielle du protocole (30/07/2026, voir `docs/journal.adoc` et `docs/protocol-i2c-leds.adoc`), la lecture d'état a été confirmée avec certitude (somme de contrôle vérifiée sur une trame réelle), mais l'écriture reste sans effet — y compris avec l'outil de référence original compilé et exécuté directement sur notre exemplaire. Le registre de confirmation (`0x80`) renvoie systématiquement `0x02`, jamais le `1` attendu. Recherche dans les issues du dépôt amont : https://github.com/miskcoo/ugreen_leds_controller/issues/111 rapporte exactement la même valeur sur un *DXP4800GT* (plateforme AMD), attribuée par le rapporteur à une différence de firmware propre au GT.

*Ce qui rend notre relevé utile à publier* : notre exemplaire est un *DXP2800* (Intel N100) — un des modèles sur lesquels l'outil a justement été validé à l'origine, pas une variante GT. Si la même anomalie s'y produit, l'hypothèse « spécifique au firmware GT » de cette issue est probablement incomplète ; le phénomène semble plus large que ce qu'elle suppose.

[source]
----
Seeing the exact same confirmation register value (0x80 == 2, never 1)
on a different, non-GT unit: a DXP2800 (Intel N100), one of the models
this tool was originally reverse-engineered against — not an AMD/GT
variant.

Read is solid: captured a real 11-byte frame from the chip and verified
its checksum independently, matches the documented format exactly.

Write is not: `power -off` runs with no error but no visible effect;
`power -on` reports "failed to change status!". `is_last_modification_
successful()` reads register 0x80 and consistently gets 2, not 1 -
matching this issue exactly, on hardware this issue's own theory
(GT-specific EC firmware) wouldn't predict.

Ruled out before concluding this is chip-side: two different Python
SMBus libraries (classic `smbus` and `smbus2`) fail identically; the
write payload matches `_change_status()`/`compute_checksum()` byte for
byte; no `led_ugreen`-style kernel module is loaded; no LED class device
for this controller appears under /sys/class/leds/ (only the NIC and
keyboard LEDs do). This was tested under a live Linux environment
(SystemRescue) that has never talked to this controller from any host
before — if that matters, it might be worth documenting as a
prerequisite.

Happy to run further tests if useful — have a few more UGREEN units
available (details: https://github.com/aloli/ugreen-hal, an
in-progress FreeBSD port of the LED/GPIO/hwmon hardware for this NAS
range).
