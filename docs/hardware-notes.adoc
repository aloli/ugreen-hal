= Relevés matériels — UGREEN NASync
:toc:
:sectnums:

Ce document consigne, modèle par modèle, les relevés matériels effectués physiquement (numéros de puce, adresses de bus, pilotes Linux déjà chargés par UGOS). Contrairement à la documentation UGREEN officielle, ces informations sont volontairement précises et vérifiables : chaque ligne provient d'une observation directe (photo de console, sortie de commande), pas d'une supposition.

=== Supervision matérielle (watchdog, buzzer, capteurs)

[cols="2,3"]
|===
|Champ |Valeur

|Chip
|ITE IT8613, révision 8613.12 (ligne `Found chip IT8613 rev 8613. 12`)

|Watchdog
|Exposé sous Linux comme « IT87 WDT », `/dev/watchdog0`. Sous UGOS, le pilote programme un timeout de 20 minutes. +
*Confirmé sur matériel le 28/07/2026* : ce watchdog est *actif au niveau du BIOS*, et beaucoup plus agressif que ne le laissait croire le chiffre de 20 minutes relevé sous UGOS. Démarré sur SystemRescue, sans aucun pilote pour le « nourrir », le DXP2800 *redémarre de lui-même en moins d'une minute*, puis repart sur UGOS (l'eMMC interne, entrée `debian` du menu de démarrage). Le délai par défaut armé par le BIOS est donc de l'ordre de la dizaine de secondes, bien inférieur aux 20 minutes que le pilote UGOS impose une fois chargé. +
*Conséquence* : sans désactivation préalable, aucune session utile n'est possible sous un système alternatif — la machine redémarre avant qu'on ait le temps de travailler. La désactivation se fait dans le *Setup* du BIOS (`Ctrl-F12` → `Enter Setup`), et non par le menu de démarrage ponctuel. Cohérent avec le retour communautaire : « Ctrl-F12 on boot to get into the BIOS, disable the watchdog, set boot device appropriately » (https://forums.truenas.com/t/actual-installs-on-ugreen-hardware-observations-experiences-tips/6910). Intitulé exact de l'option et emplacement dans les menus : *à relever au prochain passage dans le Setup*

|Buzzer
|Ligne `DXP2800 SATA&beep init` observée pendant le chargement du pilote UGREEN

|Statut FreeBSD
|Le framework `superio(4)` reconnaît déjà l'identifiant IT8613 (review Phabricator D39969, acceptée). Le pilote complet de supervision (`it8613hwm(4)`) existe en review (D39970/D39971) mais n'est *pas* intégré : statut « Changes Planned », bloqué par un conflit avec le code thermique ACPI. C'est une piste de contribution amont directe plutôt qu'un développement from scratch.
|===

=== Services UGOS observés (contexte, non prioritaire pour le portage)

Pour mémoire, UGOS fait tourner un ensemble de services propriétaires au-dessus de ce Debian : `ugdriver.service`, `humonitor.service`, `ugbus.service` (bus de message interne), `storage_serv`, `discovery_serv`, `domain_tool` (en échec au démarrage observé), `taskmgr_serv`, `thumb_serv`, `gateway_serv`, `transcode_serv`, `entry_serv`/`startx` (interface graphique X11), ainsi que PostgreSQL (`ugreen-psql`) et Redis en interne, nginx en reverse proxy. Ces services ne concernent pas le projet (ils disparaissent avec UGOS), mais expliquent pourquoi le journal de démarrage est aussi chargé.

=== Paquet de firmware UGOS (analyse du 20/07/2026)

Analyse d'un paquet téléchargé depuis le centre de téléchargement UGREEN : `release_20260624-firmware_image-1.17.0.95-intel_release_amd64_6.18.img`, 1,75 Gio, version 1.17.0.0095, compilé le 30/06/2026.

Le paquet lui-même n'est pas versionné dans ce dépôt : il pèse 1,75 Gio par version et contient du code propriétaire UGREEN, qui n'a pas à être redistribué depuis un dépôt public sous licence BSD. Seules les conclusions sont consignées ici.

[cols="2,3"]
|===
|Constat |Détail

|Format réel
|Archive *tar GNU*, malgré l'extension `.img`. Ce n'est donc pas une image disque écrivable telle quelle sur un périphérique bloc — `dd` sur cette archive ne produirait rien d'amorçable.

|Contenu
|Un système complet : `rootfs-base.squashfs` (792 Mo), `kernel.squashfs` (86 Mo), `fw.squashfs` (156 Mo), `apt.squashfs` (142 Mo), `oem.squashfs`, `vmlinuz`, `initrd.img`, plus `ugreen.bz2` (496 Mo). Accompagné de deux exécutables : `ugupdate` (13 Mo) et `ugpt` (« ugreen package tool », archive auto-extractible Makeself).

|Point d'entrée
|`ugospro-upgrade`, script de trois lignes qui appelle `ugpt upgrade -i "$1" -a amd64`. Le verbe est explicitement *upgrade*.

|Version minimale requise
|`ugreen-os-release.json` déclare `min_version: 1.12.0.1`. Le paquet suppose donc une installation UGOS *déjà présente*, d'une version au moins égale.

|Système
|Debian GNU/Linux 12 (bookworm), noyau 6.18, `amd64` — cohérent avec les relevés de console du sprint 0.
|===

*Conséquence pour la stratégie de sauvegarde.* Deux affirmations opposées ont circulé sur ce projet, et aucune n'est exacte :

* « UGREEN ne fournit aucune image de restauration » — *faux*. Le paquet contient bien l'intégralité de la matière nécessaire à reconstruire un système : racine, noyau, initrd, et même un outil de partitionnement.
* « Le firmware étant téléchargeable, la sauvegarde est inutile » — *non démontré*. Le point d'entrée documenté est une mise à niveau exigeant une installation préexistante en version ≥ 1.12.0.1. Sur un eMMC effacé, il n'y a rien à mettre à niveau.

L'inconnue qui subsiste : `ugpt` accepte-t-il d'autres verbes qu'`upgrade` — une installation à nu, une restauration ? Sa charge utile est une archive Makeself qui n'a pas pu être ouverte proprement lors de cette analyse. Tant que ce point n'est pas tranché, *le clone de l'eMMC reste la seule voie de retour certaine*, et il ne coûte qu'une soirée.

=== Chaîne de démarrage (bootloader)

[cols="2,3"]
|===
|Champ |Valeur

|Bootloader
|GNU GRUB version 2.06-3~deb11u4 (paquet issu de Debian 11, alors que l'userland est du Debian 12 « bookworm » — probablement un héritage de l'image de base, sans conséquence directe)

|Entrée de boot observée
|Une seule entrée, nommée `UGOSPRO-NAS` (label générique de la ligne de firmware, indépendant du hostname réseau `DXP2800-2CFF`)

|Touche d'accès au BIOS
|*`Ctrl-F12` au démarrage — confirmé sur matériel le 28/07/2026.* Ouvre un menu de sélection du périphérique de démarrage à trois entrées : `debian` (UGOS sur l'eMMC interne), `UEFI: USB` (le support externe), et `Enter Setup` (configuration du BIOS). *Distinction importante* : `UEFI: USB` est un démarrage ponctuel, à usage unique — au redémarrage suivant, la machine reprend son ordre par défaut (`debian`). Pour un réglage durable (ordre de démarrage, désactivation du watchdog), il faut passer par `Enter Setup`, pas par ce menu ponctuel

|Écran affiché avant GRUB
|Un splash avec le logo « UGREEN » s'affiche avant le menu GRUB — confirme que la sortie HDMI est active dès les toutes premières étapes du démarrage, cohérent avec les conclusions déjà tirées sur le firmware AMI standard. Mode verbeux confirmé le 20/07/2026 comme *comportement par défaut* : aucune manipulation n'est nécessaire pour obtenir le journal de démarrage complet, un simple appui sur le bouton d'alimentation suffit

|Conséquence pour le projet
|GRUB étant un bootloader standard (pas un chargeur propriétaire), il sera possible, en phase 4 (remplacement du firmware interne), d'envisager d'y ajouter une entrée pour FreeBSD/zVault plutôt que de devoir remplacer tout le mécanisme de démarrage — à confirmer le moment venu.
|===

=== Autres observations mineures

* Pilote `r8152`/`r8152-cfgselector` (USB-Ethernet Realtek) chargé au démarrage, alors qu'aucun adaptateur externe n'était branché à ce moment — probablement un chargement générique préventif plutôt que la preuve d'un port USB-Ethernet interne. Bonne nouvelle incidente : c'est la même famille de puce que l'adaptateur USB de secours déjà retenu dans le plan (TP-Link UE300, RTL8153).
* Sur ce boot, `fsck` a corrigé des compteurs de blocs/inodes libres incohérents sur la partition `USER-DATA` (arrêt précédent non propre). Sans conséquence, mais à garder en tête : préférer un arrêt propre du NAS quand possible plutôt qu'une coupure brute, pour éviter cette vérification systématique.
* `domain_tool.service` et `smbftpd.service` échouent toujours au démarrage (déjà observé lors du premier relevé) — cohérent avec l'absence de disques installés, sans lien avec notre projet.
