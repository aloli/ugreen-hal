= Protocole I2C/SMBus du contrôleur LED — UGREEN NASync
:toc:
:sectnums:

[NOTE]
====
Statut de ce document : le protocole ci-dessous est *confirmé exact sur le matériel réel*, sous Linux (30/07/2026) — lecture de bloc réelle à l'adresse `0x3a`, décodage cohérent, somme de contrôle vérifiée par calcul indépendant (voir plus bas). Ce n'est plus une simple extraction du code source de référence `miskcoo/ugreen_leds_controller`. Il reste en revanche *non testé sous FreeBSD* — c'est l'objet du sprint 3 du plan de projet, une fois le NAS de test disponible sous zVault. Le format de trame Linux confirmé ici (bloc « i2c », sans octet de longueur) est précisément le point d'incertitude documenté plus bas pour FreeBSD.
====

== Ce qui est confirmé par observation directe (DXP2800)

À partir du journal de démarrage du noyau Linux d'UGOS (sprint 0, deux relevés concordants) :

* Le contrôleur LED est vu par le noyau comme un périphérique sur le bus *SMBus I801* (contrôleur SMBus intégré au PCH Intel, périphérique PCI `0000:00:1f.4`, visible dans les journaux comme `i801_smbus`) — et non un bus I2C générique séparé. C'est une précision importante par rapport à la version précédente de ce document.
* Chip ID détecté : `0xc5b2`.
* Adresse esclave I2C/SMBus du contrôleur : `0x3a` — *attention, adresse en convention 7 bits (Linux)*. L'équivalent FreeBSD est `0x74` : voir la section « Convention d'adressage » ci-dessous, c'est le piège le plus coûteux identifié à ce jour.
* Le module Linux qui le pilote côté UGOS s'appelle `leds-mcu` (`ug_led_driver_init`), mais le projet de référence utilisé ici pour le portage est l'implémentation *espace utilisateur* de `miskcoo/ugreen_leds_controller`, plus simple à porter vers FreeBSD qu'un module noyau Linux.
* Modèle explicitement supporté par ce projet de référence : DXP2800 (voir ticket amont https://github.com/miskcoo/ugreen_leds_controller/issues/19).
* *Confirmation par sonde directe (29/07/2026)* : sous SystemRescue démarré sur le NAS de test, avec `i2c-i801`/`i2c-dev` chargés (bus `i2c-11`, contrôleur `8086:54a3` à `00:1f.4`), `i2cdetect -y -r 11` détecte un périphérique à l'adresse `0x3a`.
* *Protocole validé par lecture réelle (30/07/2026)* : voir la section « Première lecture réelle » ci-dessous. Le format de bloc, le découpage des octets et l'algorithme de somme de contrôle sont désormais confirmés par calcul indépendant sur une trame réellement reçue de la puce — pas seulement déduits du code source.

=== Première lecture réelle (30/07/2026)

`i2ctransfer` échoue sur ce contrôleur (`Error: Adapter does not have I2C transfers capability`) : `i801` n'implémente pas les transactions I2C génériques (`I2C_RDWR`), seulement le sous-ensemble SMBus. Confirme, indépendamment du code FreeBSD, que le bon point d'entrée est bien la pile SMBus et non de l'I2C brut.

Lecture réussie via le module Python `smbus` (`read_i2c_block_data`, qui utilise `I2C_SMBUS_I2C_BLOCK_DATA` — le même sous-protocole « bloc sans octet de longueur » que le code de référence) :

[source,shell]
----
python3 -c "
import smbus
bus = smbus.SMBus(11)
data = bus.read_i2c_block_data(0x3a, 0x81, 11)
print(' '.join(f'{b:02x}' for b in data))
"
----

Résultat obtenu (LED power, registre `0x81`) :

[source]
----
01 b4 ff ff ff 00 00 00 00 03 b2
----

Décodage, selon le format documenté plus haut :

[cols="1,2,3"]
|===
|Octet(s) |Valeur |Signification

|`0x00`
|`01`
|État : allumée

|`0x01`
|`b4` (180)
|Luminosité, 180/255

|`0x02`-`0x04`
|`ff ff ff`
|Couleur : blanc

|`0x05`-`0x06`
|`00 00`
|Durée de cycle : 0 ms (sans objet, pas de clignotement)

|`0x07`-`0x08`
|`00 00`
|Durée allumée dans le cycle : 0 ms

|`0x09`-`0x0a`
|`03 b2`
|Somme de contrôle
|===

*Vérification indépendante de la somme de contrôle* : somme des octets `0x00` à `0x08` = `1 + 180 + 255 + 255 + 255 + 0 + 0 + 0 + 0 = 946 = 0x03b2`. Correspond exactement aux deux derniers octets reçus. Une correspondance aussi précise sur neuf octets non triviaux exclut une coïncidence : la puce répond bien selon le protocole documenté, et notre lecture le décode correctement.

Conséquence importante pour le sprint 3 (FreeBSD) : cette lecture confirme que la puce ne renvoie *aucun octet de longueur* — les 11 octets reçus sont directement les données. Si `SMB_BREAD` sous FreeBSD implémente le « block read » SMBus standard (qui, lui, insère un octet de longueur), le résultat serait décalé. Ce point, déjà signalé dans l'encadré « Incertitude majeure » ci-dessous, est donc *renforcé* par cette confirmation Linux plutôt que résolu — seul un essai sous FreeBSD tranchera.

== Protocole (extrait du code de référence)

=== Convention d'adressage : 7 bits (Linux) contre 8 bits (FreeBSD)

[IMPORTANT]
====
*Point le plus important de ce document pour le sprint 3.* Linux et FreeBSD ne désignent pas les adresses I2C de la même façon : Linux utilise la convention *7 bits*, FreeBSD la convention *8 bits* (adresse décalée d'un bit vers la gauche, le bit de poids faible servant à distinguer lecture et écriture).

En conséquence, l'adresse `0x3a` relevée sur la console Linux d'UGOS (sprint 0) *ne désigne rien sous FreeBSD*. L'adresse à utiliser est :

[source]
----
0x3a << 1 == 0x74
----

Ignorer ce détail conduit à un échec silencieux, sans message d'erreur exploitable, que l'on est tenté d'attribuer au protocole, aux tailles de bloc ou au mauvais device node — c'est-à-dire à chercher partout sauf au bon endroit.

*Source* : fil « NASync LED controller » du forum FreeBSD (https://forums.freebsd.org/threads/nasync-led-controller.100889/), ouvert le 21/12/2025 par un utilisateur travaillant sur un NASync sous FreeBSD 14.3-RELEASE, resté bloqué cinq semaines sur ce point précis, jusqu'à la réponse du 26/01/2026 : « FreeBSD and Linux use different conventions when talking about I2C addresses, 8-bit and 7-bit. If you do the math, 0x74 == 0x3a << 1. »

*Statut* : non encore vérifié sur notre propre matériel — à confirmer au sprint 3, avant toute conclusion sur le reste du protocole.
====

=== Bus et adressage

* Bus : SMBus I801 (`/dev/i2c-N` détecté sous Linux via `/sys/class/i2c-dev/*/device/name` commençant par `SMBus I801 adapter`).
* Adresse esclave : `0x3a` en convention Linux (7 bits), soit *`0x74` en convention FreeBSD* (8 bits) — voir l'encadré ci-dessus.
* Transactions utilisées : SMBus *block* read/write (`I2C_SMBUS_I2C_BLOCK_DATA` côté Linux), pas de simples transactions octet-à-octet.

=== Identifiants de LED

[cols="1,3"]
|===
|ID |LED

|`0`
|Indicateur d'alimentation (power)

|`1`
|Indicateur réseau (netdev)

|`2`, `3`, ...
|Indicateurs de disque « disk1 », « disk2 », etc. (jusqu'à `9` = disk8 sur les modèles 8 baies ; le DXP2800 n'utilisera vraisemblablement que `2` et `3`, à confirmer une fois des disques installés)
|===

=== Lecture d'état — bloc SMBus de 11 octets à l'adresse `0x81 + ID`

[cols="1,3"]
|===
|Octet |Signification

|`0x00`
|État : 0 (éteint), 1 (allumé), 2 (clignotant), 3 (respiration/breath)

|`0x01`
|Luminosité

|`0x02`-`0x04`
|Couleur RGB (rouge, vert, bleu)

|`0x05`-`0x06`
|Durée totale d'un cycle blink/breath, en ms (poids fort puis poids faible)

|`0x07`-`0x08`
|Durée « allumé » dans un cycle blink/breath, en ms (poids fort puis poids faible)

|`0x09`-`0x0a`
|Somme de contrôle des octets `0x00`-`0x08` (poids fort puis poids faible)
|===

Exemple donné par le projet de référence (lecture brute via `i2cget`, illustrant un indicateur d'alimentation violet, clignotant, allumé 40 % du temps, luminosité 180/256) :

[source,shell]
----
i2cget -y 0x01 0x3a 0x81 i 0x0b 0x02 0xb4 0xff 0x00 0xff 0x03 0xe8 0x01 0x90 0x04 0x30
----

=== Écriture d'état — bloc SMBus de 12 octets à l'adresse `0x00 + ID`

[cols="1,3"]
|===
|Octet |Signification

|`0x00`
|Identifiant de la LED (doit être répété ici, en plus d'être l'adresse/commande SMBus elle-même)

|`0x01`
|Constante `0xa0`

|`0x02`
|Constante `0x01`

|`0x03`, `0x04`
|Constante `0x00`

|`0x05`
|Sous-commande : `1` = luminosité, `2` = couleur, `3` = on/off, `4` = clignotement, `5` = respiration

|`0x06`-`0x09`
|Jusqu'à 4 paramètres, selon la sous-commande (voir ci-dessous)

|`0x0a`-`0x0b`
|Somme de contrôle des octets `0x01`-`0x09` (poids fort puis poids faible)
|===

Paramètres selon la sous-commande :

* *Luminosité* (`0x01`) : un seul paramètre, la luminosité (0-255).
* *Couleur* (`0x02`) : trois paramètres, R puis G puis B.
* *On/off* (`0x03`) : un seul paramètre, `0` ou `1`.
* *Clignotement* (`0x04`) et *respiration* (`0x05`) : quatre paramètres — durée totale du cycle (poids fort, poids faible), puis durée « allumé » dans le cycle (poids fort, poids faible). Dans le code de référence, `t_high = t_on + t_off` (durée totale) et `t_low = t_on` (durée allumée), tous deux en millisecondes.

=== Registre de statut de la dernière modification

Lecture d'un octet à l'adresse `0x80` : renvoie `1` si la dernière écriture a réussi.

== Conséquence pour le portage FreeBSD

Point important corrigé par rapport à la version précédente de ce document : comme le contrôleur est sur le bus *SMBus I801* et que le projet de référence utilise explicitement des transactions *SMBus block* (pas de l'I2C générique), le point d'entrée FreeBSD le plus probable n'est pas `iic(4)` seul, mais la pile SMBus de FreeBSD :

* Le contrôleur SMBus intégré au PCH Intel est pris en charge sous FreeBSD par le pilote `ichsmb(4)`, qui expose un bus `smbus(4)` généraliste, accessible en espace utilisateur via `/dev/smb0` (ou similaire) et l'API définie dans `<dev/smbus/smb.h>`.
* *Réserve sur cette hypothèse (ajoutée le 20/07/2026)* : le fil « NASync LED controller » du forum FreeBSD rapporte que, sur un NASync sous FreeBSD 14.3, le contrôleur n'apparaît *pas* sous le nom `I801` comme sous Linux, mais comme « Intel Alder Lake SMBus controller » (port `0xefa0`). Le même auteur signale que `iic1` et `smb2` sont tous deux adossés à `iicbus1` mais renvoient des adresses différentes selon que l'on interroge le bus via `i2c(4)` ou `smbmsg(4)`. Le nom exact du device node et le bon point d'entrée (`smbus(4)` ou `iic(4)`) sont donc à *déterminer par observation* au sprint 3, et non à supposer.
* *Identité PCI confirmée sur notre matériel (28/07/2026)* : `lspci -nn` sous SystemRescue donne `00:1f.4 SMBus [0c05]: Intel Corporation Alder Lake-N SMBus [8086:54a3]`. Le point à vérifier au premier démarrage zVault est donc précis : `ichsmb(4)` reconnaît-il l'identifiant `8086:54a3` ? S'il ne s'attache pas, `/dev/smb0` n'apparaîtra pas, et le repli est soit un pilote plus récent, soit `iic(4)`. Le banc QEMU n'aide pas sur ce point précis : il émule un ICH9, pas cette puce.
* *Balayage du bus rapporté par ce même fil* : périphériques détectés aux adresses `0x10`, `0x74`, `0x88`, `0x94`, `0xa4`. La présence de `0x74` corrobore la conversion 7 bits → 8 bits décrite plus haut.
* FreeBSD expose des ioctls SMBus (transactions quick/byte/word/block) directement analogues aux transactions `I2C_SMBUS_I2C_BLOCK_DATA` utilisées par le code Linux de référence — la traduction du protocole ci-dessus devrait donc être directe, sans avoir besoin de reconstruire les trames à la main sur un bus I2C générique.
* *Question des tailles de bloc : réglée le 20/07/2026.* La lecture directe de `sys/dev/smbus/smb.h` (dépôt FreeBSD) donne `SMB_MAXBLOCKSIZE 32` : nos blocs de 11 et 12 octets passent sans difficulté.
* *Noms d'ioctls corrigés le 20/07/2026*, également par lecture de l'en-tête réel : les macros sont `SMB_BWRITE` (`_IOW('i', 10, struct smbcmd)`) et `SMB_BREAD` (`_IOWR('i', 11, struct smbcmd)`). La version précédente de ce document mentionnait un `SMB_WRITE_BLOCK` qui *n'existe pas*.
* La structure `struct smbcmd` comporte les champs `cmd`, `reserved`, `op`, les unions `wdata`/`rdata`, puis `slave`, `wbuf`, `wcount`, `rbuf`, `rcount`. L'adresse de l'esclave se place donc dans `slave`, et l'octet de commande (`0x00 + ID` ou `0x81 + ID`) dans `cmd`.
* Reste à vérifier au sprint 3, sur le NAS réel : que `ichsmb(4)` détecte bien le contrôleur SMBus du DXP2800 — voir la réserve ci-dessus sur son nom d'attachement.

=== Incertitude majeure : octet de longueur du bloc

[IMPORTANT]
====
Identifiée le 20/07/2026 en écrivant `src/cli/ugreen-led-ctl.c`, et non encore levée. C'est le point le plus susceptible de faire échouer le premier essai.

Le code Linux de référence utilise `I2C_SMBUS_I2C_BLOCK_DATA`, une transaction I2C *brute* qui n'émet pas d'octet de longueur. `SMB_BWRITE` de FreeBSD implémente le « Block Write » du standard SMBus, lequel insère un octet de comptage entre la commande et les données :

[source]
----
Linux   (I2C block)  : [adresse][commande][d0][d1]...[dn]
FreeBSD (SMBus block): [adresse][commande][n][d0][d1]...[dn]
----

Si le microcontrôleur UGREEN attend la première forme, cet octet supplémentaire décale toute la trame et la commande est rejetée — silencieusement, selon toute vraisemblance, puisque le contrôleur n'a aucun moyen de signaler une erreur de format.

*Repli documenté* : passer par `iic(4)` et son ioctl `I2CRDWR`, qui permet de composer la trame exacte, octet par octet.

*Consigne de diagnostic* : ne pas conclure à une erreur d'adresse ou de somme de contrôle avant d'avoir écarté cette piste. Les deux hypothèses produisent le même symptôme — aucune réaction de la LED.
====

== Grille de lecture des erreurs, pour l'essai sur matériel (sprint 3.3)

Établie le 21/07/2026 sur le banc QEMU, dont la machine `q35` émule un contrôleur SMBus ICH9 auquel `ichsmb(4)` s'attache. Le programme y a été exercé contre un bus réel où aucun périphérique ne répond à l'adresse visée.

*Ce que le banc a déjà démontré* : le noyau FreeBSD accepte la forme de nos ioctls. `SMB_BREAD` a renvoyé `ENXIO` (« Device not configured »), erreur émise par la couche SMBus *après* avoir émis la transaction sur le bus, faute d'acquittement. Une `struct smbcmd` mal remplie aurait été rejetée en amont avec `EINVAL`, sans jamais atteindre le bus. La structure et les ioctls sont donc validés par l'implémentation elle-même, et non plus seulement par lecture de l'en-tête.

Sur le DXP2800, le code d'erreur discriminera les hypothèses :

[cols="1,2,3", options="header"]
|===
|Erreur |Signification |Conclusion à en tirer

|`ENXIO` +
« Device not configured »
|La transaction a été émise, personne n'a acquitté à cette adresse.
|*L'adresse est fausse, ou le contrôleur est sur un autre bus.* Vérifier d'abord la conversion 7 bits → 8 bits (`0x74`), puis l'existence d'un second `/dev/smbN`. C'est aussi l'erreur obtenue en VM, où aucun matériel ne répond : elle ne dit rien du protocole.

|`EINVAL` +
« Invalid argument »
|Le noyau a refusé la requête avant de toucher au bus.
|*La requête est malformée* : taille de bloc hors limites, champ incohérent. Rien à voir avec le contrôleur UGREEN — c'est notre code qu'il faut corriger.

|`EBUSY` / `ETIMEDOUT`
|Le bus est occupé ou n'a pas répondu à temps.
|Un autre pilote se dispute le bus, ou le contrôleur est dans un état instable. Vérifier qu'aucun pilote de supervision matérielle ne le sollicite simultanément.

|*Succès, mais la LED ne bouge pas*
|La trame est passée, le microcontrôleur ne l'a pas comprise.
|*C'est le scénario de l'octet de longueur* décrit plus haut. Basculer sur `iic(4)`/`I2CRDWR` pour émettre la trame exacte, sans octet de comptage.

|*Succès, et la LED réagit*
|Le protocole est validé.
|Passer à l'étape 3.5 : étendre à l'ensemble des LED, puis à la lecture d'état.
|===

[IMPORTANT]
====
La distinction `ENXIO` / `EINVAL` est le principal apport de cette grille. Les deux se lisent comme « ça n'a pas marché », mais elles désignent des causes opposées : l'une accuse l'adresse ou le câblage, l'autre accuse notre code. Sans cette lecture, le réflexe naturel devant un échec est de suspecter le protocole — c'est-à-dire l'hypothèse la plus coûteuse à explorer.
====

== Squelette d'utilitaire FreeBSD (à valider au sprint 3)

Le squelette ci-dessous remplace la version précédente (basée sur `iic(4)`) par une approche basée sur `smbus(4)`, cohérente avec la découverte ci-dessus. Il reste à valider sur le matériel réel — en particulier le chemin exact du device node, qui peut être `/dev/smb0` ou un autre index selon l'énumération des bus SMBus/I2C du DXP2800.

[source,c]
----
#include <sys/types.h>
#include <sys/ioctl.h>
#include <dev/smbus/smb.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

/* Adresse du contrôleur LED.
 *
 * Relevée à 0x3a sur la console Linux d'UGOS (sprint 0), mais Linux
 * exprime les adresses I2C sur 7 bits et FreeBSD sur 8 bits : il faut
 * donc décaler d'un bit. 0x3a << 1 == 0x74.
 *
 * Utiliser 0x3a tel quel sous FreeBSD ne désigne aucun périphérique et
 * échoue sans message exploitable — voir la section « Convention
 * d'adressage » de ce document. */
#define UGREEN_LED_SMB_ADDR   0x74   /* = 0x3a << 1, à confirmer sprint 3 */
#define UGREEN_LED_POWER      0
#define UGREEN_LED_NETDEV     1
#define UGREEN_LED_DISK1      2
#define UGREEN_LED_DISK2      3

static uint16_t
checksum(const uint8_t *data, size_t n)
{
	uint32_t sum = 0;
	for (size_t i = 0; i < n; i++)
		sum += data[i];
	return (uint16_t)sum;
}

/* Allume/éteint une LED — sous-commande 0x03, un seul paramètre.
 * TODO (sprint 3.2) : confirmer le device node SMBus exact et la
 * disponibilité de SMB_WRITE_BLOCK sous FreeBSD pour ce contrôleur
 * avant tout envoi réel sur le matériel. */
int
ugreen_led_set_onoff(int fd, uint8_t led_id, uint8_t on)
{
	uint8_t block[12];

	block[0] = led_id;
	block[1] = 0xa0;
	block[2] = 0x01;
	block[3] = 0x00;
	block[4] = 0x00;
	block[5] = 0x03;      /* sous-commande : on/off */
	block[6] = on ? 1 : 0;
	block[7] = 0x00;
	block[8] = 0x00;
	block[9] = 0x00;

	uint16_t sum = checksum(block + 1, 9);  /* octets 0x01-0x09 */
	block[10] = (sum >> 8) & 0xff;
	block[11] = sum & 0xff;

	struct smbcmd cmd;
	memset(&cmd, 0, sizeof(cmd));
	cmd.slave = UGREEN_LED_SMB_ADDR;  /* 0x74 — convention 8 bits FreeBSD */
	cmd.cmd = led_id;        /* adresse "commande" SMBus = 0x00 + ID */
	cmd.wbuf = block;
	cmd.wcount = sizeof(block);

	/* NOTE : l'ioctl exact (SMB_WRITE_BLOCK ou équivalent) et la
	 * structure smbcmd doivent être confirmés dans <dev/smbus/smb.h>
	 * de la version de FreeBSD ciblée — à valider au sprint 3.1/3.2. */
	return ioctl(fd, SMB_WRITE_BLOCK, &cmd);
}

int
main(void)
{
	int fd = open("/dev/smb0", O_RDWR);
	if (fd < 0) {
		perror("open /dev/smb0");
		return 1;
	}

	/* Premier test prudent (sprint 3.3) : une seule LED, un seul
	 * changement d'état, observation physique du résultat avant
	 * toute automatisation. */
	ugreen_led_set_onoff(fd, UGREEN_LED_POWER, 1);

	close(fd);
	return 0;
}
----

Après chargement de `i2c-dev` (absent du premier `modprobe`, à charger explicitement), `i2cdetect -y -r 11` *détecte un périphérique à `0x3a`* — première confirmation par sonde active, indépendante des journaux de démarrage relus par le passé. Prochaine étape : lecture de bloc réelle via `i2ctransfer` pour valider le protocole sous Linux avant FreeBSD.
