= src/cli

Cœur du HAL : utilitaires en espace utilisateur ciblant FreeBSD, strictement indépendants de toute distribution — ils ne connaissent que `smbus(4)` et `gpio(4)`, jamais zVault ni XigmaNAS.

== ugreen-led-ctl

Pilotage des LED de façade et de baies, portage du protocole documenté dans `../../docs/protocol-i2c-leds.adoc`.

[source,shell]
----
make                         # construit ugreen-led-ctl
./ugreen-led-ctl status power
./ugreen-led-ctl on disk1
./ugreen-led-ctl color disk1 255 0 0
./ugreen-led-ctl brightness power 180
----

[IMPORTANT]
====
*Jamais exécuté sur matériel réel à ce jour.* Ce programme est le livrable de l'étape 3.2 du plan ; l'étape 3.3 consiste à le lancer sur le DXP2800 sous FreeBSD et à retranscrire ce qui se produit.

Deux incertitudes sont à lever au premier essai, dans cet ordre :

. *Le contrôleur répond-il à l'adresse attendue ?* `0x74` en convention FreeBSD 8 bits, soit le `0x3a` relevé côté Linux décalé d'un bit.
. *La forme de la trame est-elle la bonne ?* Le code Linux de référence émet une transaction I2C brute, sans octet de longueur, là où `SMB_BWRITE` insère un octet de comptage conformément au standard SMBus. Si le microcontrôleur attend la première forme, la trame sera décalée et la commande rejetée — vraisemblablement en silence. Le repli documenté est `iic(4)` et son ioctl `I2CRDWR`, qui permet d'émettre la trame exacte. Ne pas conclure à une erreur d'adresse ou de somme de contrôle avant d'avoir écarté cette piste.
====

== Transférer le binaire sur le NAS

[WARNING]
====
*Ne pas essayer de copier le programme sur la clé zVault.* Elle est écrite par `dd` depuis une image ISO : son système de fichiers est un ISO9660 en lecture seule, rien ne peut y être ajouté.
====

=== Par une seconde clé USB (aucun réseau requis)

Le moyen le plus sûr avant que le NAS ne soit joignable en SSH. Formater en *FAT32* et non en exFAT : `msdosfs` est pris en charge nativement par le noyau FreeBSD, là où l'exFAT réclame `fusefs-exfat`, absent des images d'installation.

Sur le Mac :

[source,shell]
----
diskutil list                                    # repérer la clé
diskutil eraseDisk MS-DOS UGREENHAL MBRFormat /dev/diskN
cp qemu/build/ugreen-led-ctl-freebsd-amd64 /Volumes/UGREENHAL/ugreen-led-ctl
diskutil eject /dev/diskN
----

Sur le NAS, une fois démarré :

[source,shell]
----
dmesg | tail                     # repérer la clé, typiquement da0
mkdir -p /mnt/usb
mount_msdosfs /dev/da0s1 /mnt/usb
cp /mnt/usb/ugreen-led-ctl /root/
chmod +x /root/ugreen-led-ctl    # FAT32 ne conserve pas le bit d'exécution
umount /mnt/usb
----

Le `chmod` n'est pas optionnel : FAT32 ne sait pas représenter les permissions Unix, et le fichier arrivera non exécutable.

=== Par le réseau, une fois zVault joignable

[source,shell]
----
scp qemu/build/ugreen-led-ctl-freebsd-amd64 root@<ip-du-nas>:/root/ugreen-led-ctl
----

Plus commode, mais suppose le pont réseau en service et l'adresse du NAS connue — ce qui n'est pas acquis au premier démarrage.

== Compatibilité des versions de FreeBSD

[IMPORTANT]
====
Le binaire est produit sur la version de FreeBSD du banc QEMU (15.0 par défaut), alors que les cibles reposent sur des versions antérieures : *zVault sur FreeBSD 13.3*, XigmaNAS sur 14.x.

FreeBSD garantit la compatibilité *ascendante* — un binaire ancien tourne sur un système plus récent — mais jamais l'inverse. Un exécutable lié dynamiquement contre la libc de FreeBSD 15 échouerait sur 13.3, faute des versions de symboles attendues.

Deux protections, dans cet ordre :

. *Édition de liens statique*, activée par défaut dans le `Makefile` (`NO_SHARED=yes`). Le programme n'utilisant que la libc, le coût se limite à quelques centaines de kilo-octets — contre une classe entière de pannes évitées au moment précis où l'on cherche à savoir si une LED s'allume.
. *Construire sur la version de la cible* — possible pour une seule des deux :
+
[cols="1,3"]
!===
!Cible !Correspondance atteignable

!XigmaNAS (FreeBSD 14.x)
!Oui : `FREEBSD_VERSION=14.4-RELEASE ./qemu/00-fetch-image.sh`

!zVault (FreeBSD 13.3)
!*Non.* FreeBSD 13 est en fin de vie et ses images VM ont été retirées des miroirs officiels — vérifié le 21/07/2026, seules 14.3, 14.4, 15.0 et 15.1 restent publiées. Le binaire statique est la seule protection disponible pour cette cible.
!===
====

== Prérequis d'exécution

[IMPORTANT]
====
*Charger `ichsmb(4)` ne suffit pas.* Trois modules distincts interviennent, et seul le dernier crée un device node :

[cols="1,3"]
!===
!Module !Rôle

!`ichsmb(4)`
!Attache le contrôleur SMBus intégré au PCH Intel (`intpm(4)` sur d'autres plateformes).

!`smbus(4)`
!Fournit le bus SMBus lui-même.

!`smb(4)`
!*Expose `/dev/smbN` à l'espace utilisateur.* C'est celui qu'on oublie.
!===

Vérifié sur le banc QEMU le 21/07/2026 : avec `ichsmb.ko` et `smbus.ko` chargés et un contrôleur correctement attaché, `/dev/smb*` n'existait toujours pas. Symptôme trompeur — `dmesg` montre un bus parfaitement fonctionnel, mais rien ne le rend accessible depuis un programme.
====

[source,shell]
----
sudo kldload smb            # tire ichsmb et smbus par dépendance
ls -l /dev/smb*             # le device node doit exister
dmesg | grep -i smb         # vérifier l'attachement du contrôleur
----

[TIP]
====
Sans privilèges, `kldload` échoue sur `Operation not permitted` — message qui évoque une restriction de sécurité du noyau (securelevel, MAC) alors qu'il ne s'agit que d'un `sudo` manquant. Constaté sur le banc le 21/07/2026.

Pour rendre le chargement permanent, plutôt que de le refaire à chaque démarrage :

[source,shell]
----
echo 'smb_load="YES"' >> /boot/loader.conf
----
====

Le device node attendu est `/dev/smb0`, modifiable par l'option `-d`. Sur un NASync sous FreeBSD 14.3, un utilisateur a rapporté que le contrôleur apparaît comme « Intel Alder Lake SMBus controller » et non sous le nom `I801` connu de Linux — le nom exact reste donc à constater plutôt qu'à supposer.
